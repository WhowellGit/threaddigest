# Panel on the testing methodology, operator workflows, failure modes, the engineering workflow, and SQLite (2026-09-14)

**Trigger.** Wes asked, while the first external packet was being prepared, for a thorough pass over the testing mechanisms and methodology, the operator's day-to-day workflows and what typically breaks in tools like this, and the failure modes of constant change and unattended operation; then for a principal-engineer view of the change workflow and a SQLite specialist's view of every database-facing decision. The tree reviewed was `ee955bb` and its successors that day.

**What each seat was given.** The repository, read-only, fresh context, a brief following `docs/reference/AGENT_BRIEF.md` with the routing rows to read, the questions, and an output contract asking for findings with citations, not conclusions. Five seats ran in parallel: a **testing-methodology auditor** (in-family, Opus), an **operator-workflow reviewer** (in-family, top tier, chosen for the seat that must imagine a user), a **failure-mode adversary** (Opus, with a mandatory inventory of the failures of unattended tools), a **principal engineer** on the day-to-day change workflow (Opus), and a **SQLite specialist** (Opus, with reproductions run outside the repository). One seat spawned a helper that inventoried the test node ids behind each failure mode. Findings were weighed by evidence, never tallied; every claim that changed something was checked against the tree first.

## Findings recorded for the queue, by area

**Testing methodology (auditor).** The suite asserts the query answer, never the stored bytes: every compliance check reads back through the writer's own abstraction (the search-index count via `_docsize`, counters versus deltas on the same connection), which is exactly how KI-009 and KI-010 passed; one parametrized "canary absent from every byte-producing artifact" test covers the class. Every Reddit-facing behaviour is witnessed only by the fake, written from the same design review as the services; `pytest-recording`, `responses`, and `time-machine` are declared and imported nowhere. Milestone boundaries produce prose, not artifacts: the per-milestone checklist runs in no tool, and the seven-digest reading week has no recording surface. The optional mutation run is named in the plan and does not exist. Fixtures have no ageing clock and no real shape was ever captured. The three document gates are the only ones that have fired in anger; the quarterly rule will find nearly the whole ledger UNPROVEN at once, and the review tool arrives at M3. Recommendation, confidence high: the gap is the kind of witness, not the frequency of runs; spend the next increment on byte-level assertions and one credentialed probe day before M1b.

**Operator workflows (top-tier seat).** Thirteen workflows walked against the specs. Ten gaps ranked for the rev-2 design before any M2 route: manual tags cannot exist because `post_themes.rule_pk` is NOT NULL and part of the unique key; cancel has no column and no poll; restore and import erase curation and the gate text omits it; configuration import over a diverged database re-enables stopped sources and `db init` re-seeds purged subreddits; theme delete and merge are irreversible behind a plain confirm and cascade over manual tags and feedback; a theme save while the collector holds the lock has no defined outcome and a double submit reaches a 500; paused and stopped-keep-data are one state; amber-by-design for sixty days with no copy explaining it; the operator-complete gate is keyed on the CLI tree and cannot reach UI-only curation; scrubbed text in index segments and fourteen days of backups. The coworker at M4 cannot edit static settings, place an import archive, or initialise an empty volume without a terminal. Recommendation: fix the schema and gate-reach items in the rev-2 design now, cheap; the rest are route tests.

**Failure modes (adversary).** The in-run failure surface (network, locks, crashes, paging, migrations) is the best-tested part of the tree and could not be refuted. The unrefuted assumption is that the tests cover what happens between runs over months. Designed in the plan but absent from the code, all verified by search: the off-box dead-man ping, so a schedule that stops is found by accident and Reddit's listing cap makes the gap unrecoverable; scheduled backups and a restore command, so today one corrupt file is total loss (the primitives exist and are well tested; the migration path is their only caller); the retention settings, defined and read by nothing, so backups, logs, and raw JSON grow without bound; a free-disk precondition on `run`, since disk full at run-finish leaves a stuck row with no diagnosis; signal handling, so every shutdown is a `crashed` row. Also: the search-index invariant at warning severity, the settings fingerprint stamped and never compared, the repository move unnoticed by `doctor`, a dependency upgrade unchecked against the lock. Recommendation: the first three are M1d blockers, not features. The helper's inventory confirms no tests for re-tag preservation, log or raw-JSON growth, dependency upgrades, or clock skew as application behaviour, and no jitter in the retry ladder.

**The engineering workflow (principal engineer).** The core is unusually good (one connection chokepoint, a failure-shaped migration lifecycle, a held exception policy, real positive controls); the risk is that the enforcement machinery has outgrown the code it guards, and three strong-looking guarantees were weaker than they read: the merge stamp (items 2 and 3 above), the post-migration search-index check (count equality with no write after the upgrade, a proxy that cannot fail if the sync triggers vanish), and the structured logs (a column shipped, nothing writes it; the launchd log is unrotated and, until KI-010 is fixed, may hold content). Fixtures hold only live rows and cannot falsify an expand-and-contract migration. Two pinning systems (pre-commit's ruff revision and the lock file) reconcile nowhere. The register surface includes the ratchet files, so over half of commits at the current rate will need a row and a record from 2026-09-15; the seat recommends dropping that path from the surface. The memory audit in `make check` can turn the check red for reasons unrelated to the change. Best practices followed, violated, and over-applied are listed with evidence in the seat's return; the over-applied column is the guard count against "hold the count", the register surface, and documentation volume.

**SQLite (specialist).** Items 5 to 8 above, plus: the post-migration verification runs `integrity_check` and `foreign_key_check` but not the FTS integrity check, which is the object a batch migration breaks silently; the batch checklist lives in a migration docstring, review-only, and trigger loss is silent while view loss is loud; pragmas are per-connection, so the raw connections in the backup module (read-only today) and any break-glass tool run without `secure_delete` and `foreign_keys`; `busy_timeout` differs between the engine and those raw connections; `VACUUM INTO` belongs on anything retained and the backup API on the pre-migration copy; the `rank = 1` FTS integrity check is correct and should be kept; the fingerprint's exclusions are right but hide the sequence reset and a table left behind by a crashed migration; nothing checks that the data directory is a local volume. Recommendation: one branch for the four small fixes (the `WHEN` clause, `optimize` after a scrubbing run, a checked checkpoint, `hide_parameters=True`), then the migration-checklist tests before the next migration on posts or comments.

## Verdict

Five seats, five different angles, and the findings that changed the tree the same day were all in the newest code, which is the pattern to expect: the older core survived every attempt at refutation, the day's enforcement work did not. The queue on the status page is ordered by cost: the SQLite branch first because it closes four open compliance issues with four small changes, the timezone fix, then the between-run controls before the schedule goes live, then the migration-checklist tests before the next migration, then the storage-level canary class, then the rev-2 design items from the workflow seat. Confidence high on the queue's first three tiers, medium on the rest.
